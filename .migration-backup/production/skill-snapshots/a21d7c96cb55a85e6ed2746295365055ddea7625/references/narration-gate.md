# 前台文案门控

## 每次生成与审核都加载
- 目标：普通观众因具体问题、反差、玩法和真实可见的结果愿意继续看。逐段先回答“看见什么、好奇什么、这句推进了什么”，再写自然可说的大白话。娱乐性不授权虚构事实、反应或夸大效果。
- 后台单独保存事实、来源链接/日期、证据、素材入出点、权利和未确认项；前台只交故事正文、相应字幕及获批画面文字。不能把后台字段拼进口播，也不能由审核器自动添加媒体署名、出处脚标或核验过程说明。
- 将本门控同时传入生成、改写、审核与失败重试。不得仅在初稿提示中加载，或只传技能名/摘要而漏掉正文。旧缓存稿、新闻输入和通用“增强可信度、补足来源、写成报道”模板不能覆盖它。审核发现事实风险时，先回后台补证据、收窄/删除不成立的主张、调整故事；不要靠添一段“据报道/尚待验证”让不可展示的故事过关。用户本次明确改成新闻解读或要求引用时按其具体范围处理，仍遵守准确性与权利要求。

## 三道硬门
1. **内容门：** 把最终口播、字幕及自加叠字逐句检查。默认拒绝“据 IT 之家报道”“某媒体援引消息称”“据官方资料介绍”“我们核验了多家报道”“尚未独立验证/具体以官方为准”等新闻播报、来源展示和过程性自证。它们出现在后台记录不构成违规；出现在前台则必须改写或记录逐条必要例外。删署名前须重新检查主张是否有足够证据，禁止把传闻删成确定事实。
2. **素材门：** 开头与核心能力/效果段必须对应已获取并检查的真实素材，记录可见动作/结果及入出点；审稿时打开核对，链接、报道文字和计划录屏不等于已验证素材。真实静态图可用于合适的事实，不能冒充连续演示。缺素材则缩小题目、继续取材或保留“待补素材”状态，禁止朗读报道凑时长；这不禁止向用户提交明确待补的草稿，但不得标为可制作/通过。
3. **语义门：** 去掉标题与署名仍看得懂具体人物/对象在做什么；前3秒有真实可看之处，后文兑现同一个兴趣点。逐句检查是否自然可说、是否推进事件、是否贴合可见画面、是否越过证据。纯正则检查不能替代此门。

## 必要例外，不做一刀切删词
- 谁提出观点、谁做演示、是谁的主张会影响理解时，可自然说“这是厂商放出的演示”“研究团队说……”，以免误称亲测、独立验证或已普遍可用。争议信息不宜去掉归属后当事实讲；必要时不用该段。
- 影响核心结论的可用范围、条件、演示性质或结果局限要简短保留，例如“目前还是演示”“这次只测了这一种情况”；不必读一串免责清单。
- 原素材权利标记不删除。确有许可要求的署名按许可指定位置执行；与干净画面冲突时换素材或请用户决定，不能自行免除。不能以“来源留后台”为由违反署名义务。
- 每个前台例外记录具体表面、原文、必要性及类型（理解事实/权利署名/本次用户要求）。例外记录放后台；不等于再把理由念出来。媒体自身就是故事对象时，不把媒体名称的出现误当自动违规。

## 可执行检查与退回反例
运行 `python scripts/qa_narration.py 稿件检查.json`。输入包含 narration（字符串）、subtitles/overlays（字符串数组）、segments（对象数组：text、visual、material_status，后者可为 checked/pending/blocked），可选 exceptions（surface、text、kind、reason）。surface 是 narration/subtitles/overlays；kind 是 understanding/rights/user_request。一个 checked 状态仍须有实际核查证据，不能为了绿灯手填。可运行 `--self-test` 验证检测器。脚本返回非零就停在待修/待补状态；零只代表机器预检通过，须再完成三道人工门并保存结果。

- 退回：“据 IT 之家报道，这款 AI 能改变游戏。”仅改成“这款 AI 能改变游戏”仍不合格：范围是否被夸大、对应玩法/改动前后素材是否真实，均须查明。
- 退回：“画面还没找到，先把几篇报道串成一分钟。”应补真实素材或收窄题目，不能把阅读报道当作可视化兑现。
- 退回：口播删了署名，字幕/左下角又添“来源：某媒体”；审核器用“提高严谨性”重新加回新闻开场。
- 条件保留：“这是厂商放出的演示，角色确实绕过了桌子。”只有已打开对应原片、画面支持动作且归属对避免误解有用时才可用；不能由此推出日常使用必然可靠。
- 条件保留：媒体本身就是事件参与者，或许可规定必须显示署名。按具体必要性记录例外，不屏蔽全部媒体词，不把例外变成全稿新闻腔。
